- **Idle memory under 30 MB.** The spec's target is not reachable with a hardware D3D device: about 27 MB of the idle footprint is the AMD user-mode driver loaded by creating it, and plumb's own share is a few MB. The WARP software device would meet it (2.7 MB). *Why parked:* WARP draws on the CPU and breaks the spec's "adapter that owns the monitor" decision, for a mostly static UI. *Trigger:* a memory complaint, or a reason to drop the hardware adapter choice. *Evidence:* `docs/benchmarks.md` "Where the idle memory goes" (2026-10-11). *Status:* parked.
- **Per-view state as `Vec<Slot>` with an active index, no swapping (A1's g2).** `in_slot` would become "point `active` at that slot", and the `borrowed` swap would go. *Why parked:* every `self.tree` becomes an indexed access through `&mut self`, so most `App` methods would take a slot; decided 2026-10-31 to do the one-struct swap first (`docs/superpowers/specs/2026-10-31-view-slot-design.md`). *Spike 2026-10-31 (throwaway branch, reverted):* indexing through `slot()`/`slot_mut()` accessors in `App` alone left at least 21 borrow conflicts in 10 functions, mostly one shape: `(&self.slot().tree, &mut self.slot_mut().model)` (the tree read while the rows are updated), plus 83 sites that needed `slot_mut()`; each conflict is a local restructure (take `&mut Slot` once and destructure), not a rename, and borrowck had not yet run on the functions that failed type checking, so the count is a lower bound. After A1 a swap is one `mem::swap`, so the gain is small. *Trigger:* a third kind of per-view state that cannot live in `Slot` or `Run`, or a reason to hold several views on screen at once. *Status:* decided against.
